  ### Issues
  
  #### Critical (Must Fix)
  
  None that I could trigger on the demo targets. The first Important item below would be Critical if it fires during the demo; it is cheap to fix, so I recommend treating it as must-fix anyway.
  
  #### Important (Should Fix)
  
  1. **`app/orchestrator.py:120-138` — Discover and the static half of Analyze are not wrapped; a failure there yields grade A/100 with phases stuck "running".** Spec section 7: "Every phase is wrapped so a failure marks that phase failed ... and the run continues to Report." Only the judge and probe are wrapped. I simulated `inventory()` raising: the result is `connect=completed, discover=running, analyze=pending, probe=pending, report=completed`, `grade A, score 100`, zero findings, and an `error` event. A security grader that crashes and then displays "A 100" is the worst possible failure mode for this product, and the UI will show a permanent spinner on Discover. All five public presets inventory fine today, so the trigger is uncommon, but one odd tool schema from a custom URL is enough. Fix: wrap discover and analyze like probe (`try/except -> set("failed", msg)`), and in `run_audit`'s finally, if any of discover/analyze failed, either force F like the connect case or add an `info`/`high` finding so the grade is not a clean A.
  
  2. **`app/orchestrator.py:89` + `app/llm.py:25` — `Report.llm_usage` is cumulative across all audits in the process, not per audit.** `LLM.usage` lives on the singleton `app.state.llm`; `report.llm_usage = dict(llm.usage)` copies the running total. Verified: two sequential clean audits report `calls: 2` then `calls: 4`. This directly corrupts the hackathon's required before/after evidence (hackathon.md says it will record `llm_usage.prompt_tokens` per run) and any cost display. Tests miss it because each test builds a fresh `FakeLLM`. Fix: snapshot `dict(llm.usage)` at the start of `run_audit` and store the difference (correct for sequential runs; concurrent runs would still interleave, acceptable for the demo), or move usage into a `ContextVar`.
  
  3. **`app/prober.py:62-63` — `read_only_hint: true` bypasses the destructive-name gate, and annotations are supplied by the server under audit.** Spec 7.4 lists exactly two refusal conditions (destructiveHint true, or name/description matches the list) with no override. The implementation lets an untrusted server neutralise the only non-model safety control by setting one boolean: `delete_all` + `read_only_hint: true` is callable (the test at `tests/test_prober.py:16` asserts this). For a tool whose premise is "do not trust the server", this is a real weakness, not a nicety. Fix: drop the early return; if you want annotations to matter, use them only to *add* blocks (destructive_hint true) and never to remove one.
  
  4. **`app/prober.py:68` — substring match on short list words produces embarrassing false positives on common read-only names.** Verified: `get_information`, `format_text`, `transform`, `list_permissions` (all `'rm'`), `list_skills` (`'kill'`), `retrieval_search` (`'eval'`), `get_posts`/`postgres_query` (`'post'`), `tokenize`/`get_token_count` (`'token'`), `get_payload` (`'pay'`). The plan asked for conservative blocking (`recreate_index`), which the word-boundary regex plus substring achieves, but a demo audience seeing "Blocked by safety gate: destructive word 'rm'" on `get_information` reads it as a bug. None of the five public presets trip it today, so this is Important rather than Critical. Fix: keep the `(?<![a-z])w(?![a-z])` regex on name+description, and apply the raw substring check only for words of length >= 5 (keeps `create`/`delete`/`shell`/`upload`, drops `rm`/`pay`/`post`/`kill`/`eval`/`exec`/`drop`/`send`/`token`), or tokenise on `_`/`-`/camelCase and also match `re` + verb prefixes.
  
  5. **`app/orchestrator.py:84-96` — if anything in the `finally` block raises (seen with `store.save` on a full disk), `run.close()` never runs and every SSE subscriber hangs forever.** Verified: with a failing store the task raises `OSError`, `run.done` stays `False`, and the subscriber never receives a terminator; the browser spinner never stops and `/audits/{id}` returns a partial report. Wrap `store.save` in try/except (emit an `error` event with the message) and put `emit("done")`/`done=True`/`close()` in their own `finally`.
  
  6. **`app/judge.py:68` — `response_format={"type":"json_object"}` through LiteLLM to Anthropic models is unverified (ruling: live run deferred for lack of keys).** If the proxy rejects it with a 400, the judge fails on every audit (gracefully, per Review Focus 4) and the demo loses one of its two LLM features. Not a code defect I can prove, but it is the single highest-probability live-integration surprise. Cheap insurance: on `openai.BadRequestError` retry once without `response_format` (the parser already tolerates prose-wrapped JSON).
